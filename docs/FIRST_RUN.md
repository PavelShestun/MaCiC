# First real CI/CD run: acceptance protocol

Use this after creating a fresh GitHub repository from the template. The goal is not merely to obtain green checks; it is to deliberately break each important guarantee once and confirm that the expected gate blocks it.

## 0. Repository setup

1. Replace all placeholder teams/users in `CODEOWNERS`.
2. Push the repository to GitHub.
3. Run the ordinary `research-gates` workflow once before making its checks required.
4. Confirm the exact job names reported by GitHub, then apply the example ruleset.
5. Create a protected GitHub Environment named `research-release` and require at least one human approver for it.
6. If automated red-team review is desired, set `OPENAI_API_KEY` as a repository or environment secret and optionally set repository variable `MATH_CICD_REDTEAM_MODEL`.

Do not enable a required status check before that check has successfully reported at least once in the repository.

## 1. Baseline green run

Open a no-op documentation PR. Expected checks:

- `protocol-gate` PASS
- `unit-tests` PASS
- `acceptance-suite` PASS
- `workflow-audit` PASS
- `lean-build` PASS
- `axiom-audit` PASS
- `exact-dependencies` PASS

Download the `exact-mathematics-analysis` artifact. It should contain the exact dependency JSON/DOT, review-surface report, and environment lock generated by the CI environment.

Before destructive tests, also run locally:

```bash
researchctl acceptance
```

All built-in sabotage cases must report `PASS`; each PASS means the sabotage was correctly detected.

## 2. Invalid Lean-reference failure test

On a temporary hypothesis, deliberately swap the reference fields, for example:

```yaml
lean_file: MathCI.Example
lean_module: MathCI.bad_axiom
lean_declaration: MathCI/Example.lean
```

Expected result: `researchctl validate` fails with `INVALID_LEAN_REFERENCE`; `freeze` and `semantic-diff` must emit controlled diagnostics and must not show Python tracebacks. Revert the test.

## 3. Placeholder-proof failure test

Create a temporary branch and change a Lean proof to:

```lean
theorem deliberate_failure : True := by
  sorry
```

Expected result: `protocol-gate` fails and the PR cannot merge. Revert the test.

## 4. Frozen-statement drift test

For `H-0001`, alter the theorem header without updating its frozen hash, for example change the conclusion. Expected result:

`FROZEN_STATEMENT_DRIFT expected=... current=...`

Revert the test. This verifies that an agent cannot silently weaken or strengthen the target.

## 5. Illegal status-transition test

Change a card directly from `CANDIDATE` to `VERIFIED_RESULT` in a PR. Expected result: `protocol-gate` rejects the transition when run against the base branch.

## 6. Stale-review test

On a dedicated test hypothesis:

1. Complete a proof-understanding review and record the generated formalization fingerprint.
2. Change the Lean proof or `proofs/H-XXXX.md` without changing the theorem statement.
3. Keep the old review.

Expected result: later-stage validation reports that the proof review is stale.

Repeat analogously for:

- literature/provenance evidence -> literature review must become stale;
- formalization/toolchain evidence -> reproduction review must become stale;
- any evidence included in the final fingerprint -> final review must become stale.

## 7. Exact-dependency test

Create two project lemmas where the headline theorem uses the intermediate lemma. Run:

```bash
researchctl deps-exact H-XXXX
researchctl review-surface H-XXXX
```

Expected: the exact graph contains a project edge from the headline theorem to the intermediate lemma, even if the proof uses tactics whose source text does not make that dependency obvious.

This is the most important v0.4 acceptance test.

## 8. Axiom-audit failure test

Introduce a dedicated test theorem:

```lean
axiom Magic : False
theorem bridge : False := Magic
theorem bad_axiom : False := bridge
```

Register `bad_axiom` under a temporary H-ID and run:

```bash
researchctl freeze H-XXXX
researchctl axioms-all
researchctl audit H-XXXX
```

Expected: fresh traversal reaches the **transitive** dependency `Magic` and the default allowlist rejects it. The ordinary `#print axioms` diagnostic should also report it. Remove the test immediately afterward.

Remove the test immediately after verification.

## 9. Red-team privilege-separation test

Open a PR from a fork or untrusted branch and add the `math:redteam` label.

Verify:

1. `redteam-prepare` has no `OPENAI_API_KEY`.
2. the trusted consumer checks out the default branch, not PR head;
3. the PR artifact is read as text data only;
4. no PR-controlled script is executed in the privileged workflow;
5. oversized prompt bundles are refused.

`researchctl workflow-audit` must reject any newly introduced `pull_request_target` workflow by default.

## 10. Release-gate test

Attempt to manually run `research-release` for a non-`VERIFIED_RESULT`. It must fail.

For a genuinely completed test object, the release job must rerun governance validation, `lake build`, axiom audit, exact dependencies, evidence freshness, and packet generation before creating the release. A release tag that already exists must never be overwritten by the workflow.

## 11. Merge-queue test

If merge queue is enabled, enqueue a PR and verify that all required checks run on the `merge_group` event. A missing `merge_group` trigger would leave required checks unreported and prevent the queue from progressing.

## Acceptance criteria

The CI/CD is considered operational only after the baseline passes and tests 2-8 fail/pass exactly as described. Red-team, release, and merge-queue tests are required if those features are enabled in the project.
